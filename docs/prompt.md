# Описание приложения для планирования разработки

## Общие сведения

Необходимо разработать многопоточное приложение на golang для копирования схемы данных БД из одной базы данных в другую.
При разработке использовать современные широко используемые библиотеки.
Ведем разработку с использованием лучших современных практик.
Подразумевается, что у источника и приемника один движок и верcия СУБД.
В текущей версии приложения работаем с 3 драйверами БД - MySQL, Clickhouse и Postgres.
Копируем таблицу целиком «как её отдаёт СУБД» (MySQL/CH — SHOW CREATE TABLE, включая индексы и партиции), VIEW и materialized view — не копируем.
ClickHouse-специфика. Копировать DDL «как есть». Если у источника `ReplicatedMergeTree` с макросами `{cluster}`/`{shard}`/`{replica}` или `ON CLUSTER` — оставляем как есть. Таблицы `Distributed` копируем. `VIEW`, `MATERIALIZED VIEW` не копируем.
В Postgres нет `SHOW CREATE TABLE`, DDL нужно генерировать вручную из `pg_catalog` / `information_schema`. Генерация DDL кодом только базовый набор, ограничения документируем.
FK и порядок создания. Отключаем проверку FK на сессии (MySQL: `SET foreign_key_checks=0`; PG: создать FK после).
Все действия логируем в консоль и в файл лога с именем log и датой и временем запуска в названии. Расширение файла log. Используем slog.

## Конфигурация

Конфигурация приложения сохраняется в файле yml. По умолчанию config.yml в корне приложения.

### Параметры конфигурации

connections - список подключений к БД с их параметрами
connection - подключение со своими параметрами (уникальное имя, драйвер, адрес сервера, порт, имя БД, логин, пароль и т.п.)
Также connection включает в себя необязательные списки include и exclude в которых могут быть перечислены названия таблиц name для включения или исключения копирования их схемы.
Полный состав полей `connection`: `name`, `driver` (mysql|clickhouse|postgres), `host`, `port`, `database`, `user`, `password`, `schema` (нужно для Postgres), `include`, `exclude`.

Пароли: в YAML и поддержать подстановку `${ENV_VAR}` (и/или `.env` через `godotenv`). Нужно валидировать, что `source` и `target` — разные подключения.

## Параметры запуска

--config=<имя конфинурационного файла с путем>
--source=<имя подключения источника>
--target=<имя подключения приемника>

Нужны такжже параметры `--version`, `--help`

Нужен режим `--dry-run` (показать/сохранить DDL, но не выполнять) и/или опция __выгрузки DDL в файлы__ (`.sql`-дамп)? Полезно для отладки и для Postgres.

## Порядок работы

1. Проверка возможности подключения и наличия указанных в подключениях схем / баз данных. Если нет в приёмнике: ошибка.
2. Получение списка таблиц в источнике.
3. Проход по всем таблицам в источнике, проверка попадания в списки include и exclude если они указаны для источника. Сначала проверяется include. Если список указан и таблица в него не попадает - пропускаем. Затем проверяется exclude. Если список указан и таблица в него  попадает - пропускаем. Для приемника include и exclude не проверяются. Если таблица уже существует в приёмнике пропустить с `warn`. Формат сопоставления: точное имя таблицы или `schema.table`. Регистрозависимо. Маски (`LIKE`-шаблоны, `*`/`%`) не нужны. Если в подключении указана БД/схема — имя таблицы писать без префикса схемы или допускать оба варианта. Нужно предупреждение, если элемент из `include` не найден в источнике.
4. Для копируемых схем таблиц получение их DDL и выполнение их в базе приемнике.
5. Пункты 3, 4 выполняем как одну функцию в многопоточном режиме. Количество потоков определяется количеством логических ядер.

## Многопоточность

Число воркеров = количество логических ядер процессора.
При ошибке на одной таблице: продолжать остальные и вернуть сводку.
Нужен итоговый отчёт: всего/создано/пропущено/ошибок + ненулевой `exit code` при ошибках.
Нужна отмена по `Ctrl+C` (`signal.NotifyContext`) и таймауты (на подключение/на один DDL) в конфиге.

## Логирование

Точный формат имени файла `log_20261031_120000.log`. Файл в корне приложения.
Формат вывода: консоль — `TextHandler` (человекочитаемо, возможно с цветом), файл — `JSONHandler`. Уровень максимальный.
